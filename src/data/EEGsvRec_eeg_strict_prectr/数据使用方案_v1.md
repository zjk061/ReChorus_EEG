# 新数据组织使用方案：严格前置 CTR 数据

本文档记录当前暂定的数据组织与使用方案。该方案用于解决原始 `EEGsvRec_eeg` 数据使用方式中的特征穿越问题，同时为后续引入 Transformer 等序列模型结构保留足够的信息。

本文档只讨论样本数据如何组织和使用；模型结构如何改造以适配新数据格式，后续单独规划。

## 1. 问题背景

当前原始样本中包含多类“观看当前短视频时或观看结束后才能获得”的字段，例如：

```text
c_EEG_data_310_f
c_interest_f
c_immersion_f
c_valence_f
c_arousal_f
c_playrate_f
c_view_duration_f
end_time
```

这些字段的含义是：

- `c_EEG_data_310_f`：用户观看当前短视频时采集到的 310 维 EEG 脑电特征。
- `c_interest_f`：用户观看当前短视频后填写问卷得到的兴趣评分。
- `c_immersion_f`：用户观看当前短视频后填写问卷得到的沉浸评分。
- `c_valence_f`：用户观看当前短视频后填写问卷得到的情绪效价评分。
- `c_arousal_f`：用户观看当前短视频后填写问卷得到的情绪唤醒度评分。
- `c_playrate_f`：用户观看当前短视频后的播放比例或完成度。
- `c_view_duration_f`：用户观看当前短视频的观看时长。
- `end_time`：当前观看行为结束时间。

如果把这些字段直接作为当前样本输入来预测当前样本的 `label`，就相当于使用未来才能知道的信息预测当前反馈，构成严重的特征穿越。

新的方案必须遵循一个原则：

> 对每一条当前样本，只允许使用推荐当前 item 之前已经可获得的信息。

## 2. 新任务定义

新的严格前置 CTR 任务定义为：

> 在推荐当前 `item_id` 给当前 `user_id` 之前，使用用户静态元特征、当前候选物品静态元特征，以及该用户过去已经完成的交互序列，预测当前样本的 `label`。

每条样本仍然是一个 CTR 二分类样本：

```text
(user_id, item_id, time) -> label
```

但当前样本中不能直接使用当前 item 观看过程中或观看后才产生的信息。

## 3. 对当前意见的客观评判

### 3.1 暂不使用 session/order 特征是合理的

当前暂定先不使用：

```text
c_session_mode_c
c_session_id_c
c_video_order_f
```

理由是：

- 它们虽然有可能在推荐前可知，但语义不够稳定。
- `c_video_order_f` 可能和推荐策略、曝光位置、观看流程强耦合。
- 当前阶段先排除它们，可以降低潜在泄露风险，使实验定义更干净。

因此，新方案中这三类特征不作为当前样本输入。

### 3.2 使用原始历史交互序列优于历史均值

为了避免特征穿越，同时保留 EEG 和情绪自评分的研究价值，新方案不采用“对历史 EEG 或历史情绪评分取均值”的方式构造历史统计特征。

相反，每条样本直接携带该用户在当前样本之前的原始历史交互记录序列。

这种方式更合适，原因是：

- 均值会丢失历史交互顺序。
- 均值会丢失用户近期状态变化。
- 均值无法表达不同历史 item 对当前推荐的差异影响。
- EEG 和情绪状态具有动态变化特征，原始序列比静态统计量更有表达力。
- 原始序列天然适合后续引入 Transformer、GRU、DIN、DIEN、SASRec 等序列模型。

### 3.3 历史记录中暂定只使用 item、EEG、四类情绪评分

对于每一条历史交互记录，暂定只引入以下字段：

```text
item_id
c_EEG_data_310_f
c_interest_f
c_immersion_f
c_valence_f
c_arousal_f
```

即每条历史记录包含：

- 历史观看过的 item ID。
- 历史观看该 item 时采集到的 EEG。
- 历史观看该 item 后得到的兴趣评分。
- 历史观看该 item 后得到的沉浸评分。
- 历史观看该 item 后得到的效价评分。
- 历史观看该 item 后得到的唤醒度评分。

这些字段如果来自当前样本，会造成特征穿越；但如果来自当前样本之前已经发生的历史样本，则在预测当前 item 时已经可知，可以作为合法历史信息使用。

### 3.4 用户和物品元特征必须引入

当前样本的 EEG 和问卷评分不再作为当前输入后，模型需要更多推荐前可知的信息。因此，引入用户元特征和物品元特征是必要的。

用户元特征来自 `user_meta.csv`：

```text
u_gender_c
u_age_f
u_usage_f
```

物品元特征来自 `item_meta.csv`：

```text
i_music_tempo_f
i_count_f
i_height_c
i_width_c
i_brightness_f
i_dif_brightness_f
i_E_2D_f
i_dif_E_2D_f
i_contrast_f
i_laplace_var_f
i_color_cast_f
i_hue_f
i_dif_hue_f
i_saturation_f
i_dif_saturation_f
i_value_f
i_dif_value_f
```

这些特征在推荐当前 item 之前已经可获得，不会造成当前样本特征穿越。

## 4. 当前样本字段使用规则

### 4.1 当前样本保留基础字段

每条当前样本保留：

```text

item_id
time

```

含义：

- `user_id`：当前用户。
- `item_id`：当前候选短视频。
- `time`：当前样本发生时间，用于排序和构造历史序列。

## 5. 历史交互序列组织方式

### 5.1 核心规则

对每个用户单独按 `time` 升序排序：

```text
r1, r2, r3, ..., rt, ...
```

对于第 `t` 条当前样本 `rt`，其历史只能包含：

```text
r1, r2, ..., r(t-1)
```

不能包含：

```text
rt 本身
r(t+1), r(t+2), ...
```

即：

```text
history(rt) = [r1, r2, ..., r(t-1)]
```

这个规则是避免当前样本特征穿越和未来信息泄露的核心。

### 5.2 历史字段设计

建议新增以下历史序列字段：

```text
history_item_id
history_eeg_310
history_interest
history_immersion
history_valence
history_arousal
history_length
```

字段含义：

- `history_item_id`：历史观看过的 item ID 序列。
- `history_eeg_310`：每个历史 item 对应的 310 维 EEG 特征序列。
- `history_interest`：每个历史 item 观看后的兴趣评分序列。
- `history_immersion`：每个历史 item 观看后的沉浸评分序列。
- `history_valence`：每个历史 item 观看后的效价评分序列。
- `history_arousal`：每个历史 item 观看后的唤醒度评分序列。
- `history_length`：当前样本实际历史长度。

### 5.3 样本示意

假设某个用户的交互序列为：

```text
r1, r2, r3, r4
```

对于当前样本 `r4`：

```text
user_id = r4.user_id
item_id = r4.item_id
time = r4.time
label = r4.label
```

其历史为：

```text
history_item_id = [r1.item_id, r2.item_id, r3.item_id]
history_eeg_310 = [r1.eeg, r2.eeg, r3.eeg]
history_interest = [r1.interest, r2.interest, r3.interest]
history_immersion = [r1.immersion, r2.immersion, r3.immersion]
history_valence = [r1.valence, r2.valence, r3.valence]
history_arousal = [r1.arousal, r2.arousal, r3.arousal]
history_length = 3
```

对于该用户的第一条样本 `r1`：

```text
history_item_id = []
history_eeg_310 = []
history_interest = []
history_immersion = []
history_valence = []
history_arousal = []
history_length = 0
```

## 7. 历史序列字段存储格式建议

当前项目的 `BaseReader` 会通过 `utils.eval_list_columns()` 将字符串列解析为 Python 对象，因此历史序列字段可以用 Python list 风格字符串存储。

### 7.1 history_item_id

示例：

```text
[12, 35, 87]
```

### 7.2 一维历史评分序列

例如 `history_interest`：

```text
[1, 4, 3]
```

或：

```text
[1.0, 4.0, 3.0]
```

### 7.3 history_eeg_310

`history_eeg_310` 是二维结构：

```text
[
  [0.1, 0.2, ..., 0.310],
  [0.3, 0.4, ..., 0.510],
  [0.5, 0.6, ..., 0.710]
]
```

每个内部列表长度必须为 310。如果当前样本没有历史，则为：

```text
[]
```

### 7.4 解析安全注意事项

如果继续依赖 `eval_list_columns()`，需要保证 CSV 中的历史序列字符串是合法 Python 表达式。

后续为了工程安全，建议将 `eval` 替换为更安全的解析方式，例如：

```python
ast.literal_eval
```

## 8. 严格避免特征穿越的构造算法

构造新样本时，应按用户分组并按时间排序。

伪代码：

```python
for user_id, user_df in df.groupby('user_id'):
    user_df = user_df.sort_values('time')
    history = []

    for row in user_df:
        new_row = build_current_sample(row, history)

        current_history_record = {
            'item_id': row['item_id'],
            'eeg_310': row['c_EEG_data_310_f'],
            'interest': row['c_interest_f'],
            'immersion': row['c_immersion_f'],
            'valence': row['c_valence_f'],
            'arousal': row['c_arousal_f'],
        }

        history.append(current_history_record)
```

关键点：

```text
必须先用已有 history 构造当前样本，再把当前样本追加到 history。
```

如果先追加当前样本，再构造当前样本的历史，就会把当前样本自身放入自己的历史，造成泄露。

## 9. 空历史样本处理

每个用户的第一条样本没有历史。建议保留这类样本，并设置：

```text
history_item_id = []
history_eeg_310 = []
history_interest = []
history_immersion = []
history_valence = []
history_arousal = []
history_length = 0
```

保留原因：

- 真实推荐系统中也存在冷启动或历史不足场景。
- 模型仍可依靠用户元特征、物品元特征和当前 item 信息预测。
- 后续序列模型可以通过 padding mask 区分空历史。

如果后续只关注有历史状态建模，也可以额外构造一个过滤掉 `history_length == 0` 的版本作为对比实验。

## 10. 历史长度处理

数据组织阶段建议保留完整历史序列，不提前截断。

原因：

- 原始完整历史最灵活。
- 后续模型可以自行决定最大历史长度。
- 方便比较不同历史窗口长度。

后续模型训练时可以设置不同窗口，例如：

```text
max_history_len = 20
max_history_len = 50
max_history_len = 100
```

并采用最近 `max_history_len` 条历史记录。这属于后续模型适配问题，当前数据方案只要求原始历史序列组织正确。

## 12. 方案优点

### 12.1 严格避免当前样本特征穿越

当前样本观看后才产生的 EEG、问卷评分、播放比例、观看时长都不再用于预测当前样本，模型输入与真实推荐前可获得的信息更一致。

### 12.2 保留 EEG 和情绪自评分的研究价值

EEG 和情绪自评分没有被丢弃，而是转化为用户历史序列信息。模型后续可以研究：

- 用户过去 EEG 状态对当前推荐反馈的影响。
- 用户过去情绪状态变化对当前偏好的影响。
- 历史 item、历史 EEG、历史情绪之间的动态关系。

### 12.3 比历史均值保留更多信息

原始历史序列保留了：

- 历史 item 顺序。
- 历史 EEG 状态变化。
- 历史情绪评分动态。
- 不同历史 item 对当前推荐的潜在影响。
- 后续引入 Transformer 序列建模的空间。

### 12.4 适合后续序列模型

该数据组织方式天然适合后续引入：

```text
Transformer
GRU
DIN
DIEN
SASRec
注意力序列模型
```

## 13. 方案代价

### 13.1 数据读取和 batch 组织更复杂

历史字段是变长序列，后续需要处理：

```text
padding
mask
history_length
batch 内不同历史长度
```

### 13.2 当前模型不能直接适配

当前 `CTRLightGCN.py` 假设 EEG 是当前样本的：

```text
[batch_size, 310]
```

新方案下 EEG 会变成历史序列：

```text
[batch_size, history_len, 310]
```

或 reshape 后：

```text
[batch_size, history_len, 62, 5]
```

因此当前模型结构后续需要调整，才能使用新的历史 EEG 序列。

### 13.3 历史较长时计算开销更大

如果保留完整历史，部分用户历史较长，后续模型训练时可能增加显存和计算开销。可以在模型阶段通过 `max_history_len` 控制。

### 13.4 空历史样本需要特殊处理

`history_length = 0` 的样本需要模型支持 padding mask 或冷启动分支，否则需要过滤。

## 15. 一句话总结

新的严格前置 CTR 数据方案是：当前样本只使用推荐前可知的用户元特征、物品元特征和候选 item 信息，不再直接使用当前样本观看后产生的 EEG、问卷评分、播放比例和观看时长；同时，把当前样本之前已经发生的历史交互原封不动地组织为变长历史序列，每条历史记录包含 `item_id`、EEG 和四类情绪自评分，为后续引入 Transformer 等序列模型提供数据基础。

## 16. 当前代码修改进展记录

本节记录为适配上述“严格前置 CTR + 历史交互序列”数据使用方案，目前已经完成的代码修改、每项修改的目的，以及尚未完成的工作。

### 16.1 已完成修改：`src/utils/utils.py`

修改目的：替换原先不安全的字符串解析方式，并兼容新旧两类数据格式。

原来的 `eval_list_columns()` 会对字符串列直接执行：

```python
eval(str(x))
```

这存在两个问题：

1. 不安全，任意字符串都可能被当作 Python 代码执行。
2. 新数据方案会出现 `history_item_id`、`history_eeg_310` 等字符串形式的 list，需要更稳定的解析方式。

目前新增了：

```python
parse_maybe_list(value, col_name=None)
```

其作用是：

- 如果字符串以 `[` 或 `(` 开头，则用 `ast.literal_eval()` 安全解析为 Python list/tuple。
- 如果列名是 `c_EEG_data_310_f`，且内容是原始逗号分隔 EEG 字符串，则按逗号拆分成 float 列表。
- 普通字符串保持原样。
- 空值做安全处理。

因此它可以同时支持：

```text
原始 EEG 字段："0.1,0.2,..."
新历史 item 序列："[1,2,3]"
新历史 EEG 序列："[[...310...],[...310...]]"
```

```python
dtype=np.object
```

替换为：

```python
dtype=object
```

以避免新版 numpy 下的兼容性问题。

## 20. 当前最新修订说明：history_label、用户内时间切分与归一化

本节记录当前 `EEGsvRec_eeg_strict_prectr` 数据集相较早期设计文档的最新变化。后续理解和建模应以本节为准。

### 20.1 当前新版 train/dev/test 字段

当前 `train.csv`、`dev.csv`、`test.csv` 的字段为：

```text
user_id
item_id
time
label
c_video_type_c
history_item_id
history_label
history_eeg_310
history_interest
history_immersion
history_valence
history_arousal
history_length
```

其中 `history_label` 是新增且计划使用的历史行为字段。

### 20.2 history_label 的含义和必要性

`history_label` 表示当前样本之前的历史交互 label 序列，长度与 `history_item_id` 一致。

由于当前历史交互序列包含该用户过去的全部交互记录，其中既有正反馈样本，也有负反馈样本，如果不提供对应历史 label，模型只能知道用户过去看过哪些 item、产生了什么 EEG 和情绪评分，但不知道这些历史交互最终是正反馈还是负反馈。

这会造成严重的信息缺失。对于推荐任务而言，历史 item 是否产生正反馈是非常关键的行为信号。因此，v1 模型设计中应使用：

```text
history_label
```

作为历史 step embedding 的一部分。

### 20.3 当前数据划分策略

当前派生数据集不再沿用原始 `train/dev/test` 的 split，也不是按用户划分。

当前逻辑是：

1. 读取原始 `EEGsvRec_eeg/train.csv`、`dev.csv`、`test.csv`。
2. 合并三份原始数据。
3. 对每个用户单独按 `time` 从旧到新排序。
4. 每条样本的历史只来自该用户当前样本之前的记录。
5. 对每个用户按约 `7:1:2` 重新切分为新版 `train/dev/test`。

因此，当前新版 split 的语义是：

```text
同一用户早期行为 -> train
同一用户中期行为 -> dev
同一用户后期行为 -> test
```

这更接近“用同一用户过去行为预测未来行为”的时间序列 CTR 设定。

### 20.4 对模型设计的影响

由于当前 `train/dev/test` 都覆盖同一批用户，后续模型中可以合理使用：

```text
user_id embedding
```

它不再是完全冷用户泛化场景下的随机未训练 embedding。

但仍然不建议只依赖 `user_id`，因为 v1 的核心目标是利用：

```text
user_meta
item_meta
history_item_id
history_label
history_eeg_310
history emotion
```

共同建模用户历史状态。

基于新版 `train.csv` 生成。

当前原则是：

```text
只使用新版 train split 统计归一化参数，再应用到 train/dev/test。
```

归一化策略包括：

```text
u_age_f                  train z-score
u_usage_f                train z-score
i_count_f                log1p + train z-score
i_laplace_var_f          log1p + train z-score
其他连续 i_* 特征        train z-score
history_eeg_310          train 有效历史 step 逐维 z-score
history emotion 四项     固定 (x - 1) / 4 缩放
```

不归一化、作为 ID 或类别处理的字段：

```text
user_id
item_id
history_item_id
c_video_type_c
u_gender_c
```

不作为连续强度归一化的历史字段：

```text
history_label
history_length
```

### 20.6 当前 Reader 行为

当前 `StrictPreCTRReader` 会加载：

```text
normalization_stats.json
```

并在 Reader 侧完成连续特征归一化。

同时，当前已经将：

```text
history_label
```

加入 `StrictPreCTRReader.history_feature_names`。这意味着后续 Dataset 会把 `history_label` 注入 `feed_dict`，并在 batch 中被 padding 成：

```text
[batch_size, max_history_len]
```

### 20.8 本节总结

当前数据方案的最新状态可以概括为：

> `EEGsvRec_eeg_strict_prectr` 是一个用户内时间切分的严格前置 CTR 数据集。每条当前样本只包含推荐前可知字段和该用户当前时间之前的完整历史序列。历史序列现在包含 `history_item_id`、`history_label`、历史 EEG 和历史四类情绪评分。连续特征由 Reader 基于 train-only `normalization_stats.json` 完成归一化。后续 v1 模型设计应显式使用 `history_label`，并按“同一用户过去预测未来”的时间序列 CTR 设定建模。
