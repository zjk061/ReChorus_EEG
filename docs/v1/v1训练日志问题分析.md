## 2. 如何正确阅读这份日志

每一行训练日志的结构为：

```
Epoch N   loss=训练集BCE   dev=(ACC, AUC, F1, LOG_LOSS)
```

**务必区分以下字段，不可混为一谈：**

| 字段 | 含义 | 读法 |
|------|------|------|
| `loss=` | 训练集 **BCE 训练损失** | 只反映对训练集的拟合程度 |
| `dev LOG_LOSS` | 验证集 **对数损失** | 与训练 BCE 公式相近，但不是同一 batch 上的同一个数 |
| `dev AUC` | 排序/区分能力 | **CTR 主指标**；与 loss 方向不一定一致 |
| `dev F1` | 固定阈值 **0.5** 下的 F1 | 对阈值极敏感，当前日志里容易误导 |
| `dev ACC` | 固定阈值 0.5 下的准确率 | 负样本占 ~70%，"多预测 0" 也能有不错 ACC |

**最终应报告的性能 = 早停选出的 best checkpoint（本次为 epoch 3），不是最后一轮 epoch 12。**

## 3. 训练过程逐阶段解读

### 3.1 训练前（随机初始化）

```
Test: AUC=0.382, ACC=0.291
```

AUC 接近随机，说明初始权重几乎没有区分能力。这是正常起点。

### 3.2 第 1 轮：模型快速学到信号

```
Epoch 1: train loss=0.583 → dev AUC=0.734, F1=0.581
```

仅 1 个 epoch，dev AUC 就从 0.38 跳到 0.73。说明：

- 模型**并非学不动**，而是**很快**从静态特征（用户/物品 embedding、元特征、情境特征等）中捕获了有效信号；
- 此时历史 EEG / Transformer 是否已充分起作用，**尚不能从日志直接断定**；
- dev 仅 355 条，单轮指标波动会较大。

### 3.3 最佳 checkpoint（epoch 3）

```
Epoch 3: train loss=0.192, dev AUC=0.735, dev LOG_LOSS=0.638
```

| 指标 | Dev（best） | Test |
|------|-------------|------|
| **AUC** | **0.735** | **0.667** |
| ACC | 0.707 | 0.698 |
| F1@0.5 | 0.212 | 0.169 |
| LOG_LOSS | 0.638 | 0.728 |

**客观结论：**

- **AUC 有区分能力**：dev 0.735、test 0.667，均高于随机（0.5）；test 比 dev 低约 **6.8 个点**，存在泛化差距。
- **F1@0.5 很低，不等于模型排序能力失败**：预测概率整体偏低（dev 平均 pCTR≈0.21），用 0.5 阈值时正类预测率仅 ~6.5%（真实正样本率 ~31%）。若在 dev 上将阈值调到约 0.15，F1 可达 ~0.59。
- **ACC 偏高有"虚高"成分**：负样本占多数，保守预测仍可获得不错 ACC。

### 3.4 后期过拟合（epoch 4–12）

```
Epoch 3  → Epoch 12
train loss:     0.192 → 0.127  （持续下降）
dev LOG_LOSS:   0.638 → 1.168  （明显恶化）
dev AUC:        0.735 → 0.661  （从最佳点回落）
```

这是典型的过拟合模式：

- 训练集：继续拟合，loss 越来越低；
- 验证集：泛化变差，LOG_LOSS 升高，AUC 从峰值回落。

**早停机制有效**：在 epoch 12 触发早停，最终加载的是 epoch 3 的模型，而非过拟合最严重的最后一轮。

## 4. 对"过拟合"判断的校正

### 4.1 你的直觉：哪些是对的

- **过拟合确实存在**：train loss 持续下降，dev LOG_LOSS 后期明显升高，dev AUC 从 epoch 3 后回落。
- **训练越久并非越好**：epoch 12 的模型明显劣于 epoch 3。

### 4.2 需要修正的认知

| 常见误判 | 实际情况 |
|----------|----------|
| "验证指标全面很差" | **AUC 并不差**（dev 0.74 / test 0.67）；差 mainly 在 F1@0.5 和 LOG_LOSS |
| "train loss 和 dev LOG_LOSS 应该接近" | 小数据 + 复杂模型下，两者差距扩大是常见现象 |
| "F1 从 epoch 1 的 0.58 掉到 0.21 = 模型变差" | 更可能是**预测变保守 + 固定阈值 0.5** 导致，AUC 仍可维持 |
| "最后一轮指标代表最终模型" | 最终模型是 **epoch 3**（早停 + load best） |

### 4.3 当前核心矛盾（一句话）

> **模型容量（~28 万参数）相对数据量（2487 train / 30 用户）偏大 → 过拟合来得快 → dev/test 存在泛化 gap → 部分指标（尤其 F1@0.5）造成"全面失败"的错觉。**

### P1 — 最 urgent 的技术问题（建议优先动手）

#### 问题 3：过拟合 / 模型-数据不匹配 【最高优先级】

**证据：**

- 279,933 参数 vs 2,487 训练样本、30 用户；
- epoch 3 后 dev AUC、LOG_LOSS 持续恶化；
- epoch 1 即达 AUC 0.73，后续 train loss 仍在下降但 dev 不再提升。

**建议行动：**

1. 做 **ablation**（见 P1 问题 5），确认哪些模块在贡献、哪些在添噪；
2. 尝试 **更小模型**：减小 `emb_size`、`transformer_layers`、`fusion_hidden`；
3. 加强正则：更大 `l2`、更大 `dropout`、更小 `lr`；
4. 接受"复杂模型在小数据上收益有限"，与简单 baseline 对比。

#### 问题 4：dev → test 泛化 gap（AUC 0.735 → 0.667）

**证据：**

- 最佳 dev AUC 0.735，test AUC 0.667，差距 ~7 点；
- dev/test 均为同一批 30 用户的时序切分，test 样本更多、可能包含更靠后的交互。

**建议行动：**

1. **以 test AUC 为最终报告主指标**；
2. 检查 dev/test 的时间分布、每用户样本数是否均衡；
3. 评估 dev 切分方式是否合理（是否需要更"未来"的 dev 段）。

#### 问题 5：评估指标与早停目标不一致

**证据：**

- 早停按 **AUC** 选模型，但 LOG_LOSS / F1 后期恶化更显眼；
- F1@0.5 与模型实际排序能力（AUC）严重脱节。

**建议行动：**

1. 在训练脚本中显式写 `--main_metric AUC`；
2. 单独在 dev 上做 **阈值搜索** 后再报 F1；
3. 补充 PR-AUC 或 calibration 分析（可选，P3）。

#### 问题 6：历史 EEG / 序列模块是否真正有用

**证据：**

- epoch 1 即 AUC 0.73，怀疑静态特征（user/item meta、embedding）贡献过大；
- 无法从当前单次实验判断 v1 架构（Transformer + Cross-Attention）是否值回票价。

**建议行动（ablation 实验，最小 3–4 次运行）：**

| 实验 | 改动 | 目的 |
|------|------|------|
| A | 完整 v1 模型 | baseline |
| B | 去掉 history 分支 | 历史序列是否有增益 |
| C | 去掉 EEG，仅保留 meta + label 历史 | EEG 是否有增益 |
| D | 更小模型 / 更强正则 | 过拟合是否缓解 |

每次只改一个因素，记录 dev/test AUC 与 LOG_LOSS。
